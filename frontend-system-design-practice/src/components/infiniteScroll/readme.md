### 02. Design High-Performance Infinite Scrolling Feed
**Infinite Scrolling-এর মূল কনসেপ্ট (The Core Concept)**
Infinite Scroll হলো একটি ডিজাইন প্যাটার্ন যেখানে ইউজার যখন স্ক্রল করে কন্টেন্টের শেষের দিকে পৌঁছায়, তখন স্বয়ংক্রিয়ভাবে পরবর্তী ডাটা লোড হতে থাকে। এটি ইউজারকে "Pagination" বা "Next Page" বাটনে ক্লিক করার ঝামেলা থেকে মুক্তি দেয়।

**১. ডিটেকশন পদ্ধতি (Detection Mechanism)**
সিস্টেমটি কীভাবে বুঝবে যে ইউজার একদম নিচে চলে এসেছে? এর জন্য দুটি জনপ্রিয় পদ্ধতি আছে:

- Scroll Event (পুরানো পদ্ধতি): ব্রাউজারের scroll ইভেন্ট লিসেন করে দেখা হয় ইউজার কতটুকু স্ক্রল করেছে। এটি খুব বেশি CPU খরচ করে এবং সাইটকে স্লো (Jank) করে দেয়।

- Intersection Observer API (আধুনিক পদ্ধতি): এটি একটি স্মার্ট ব্রাউজার এপিআই। আমরা লিস্টের নিচে একটি ছোট "Sentinel" (একটি খালি div) রাখি। যখনই এই div টি ইউজারের স্ক্রিনে দৃশ্যমান হয়, ব্রাউজার আমাদের একটি সিগন্যাল দেয়। এটি পারফরম্যান্সের জন্য সেরা কারণ এটি প্রতি সেকেন্ডে ফায়ার হয় না।

**২. ডাটা ফ্যাচিং এবং মার্জিং (Data Fetching & Merging)**
১০০k ডাটার ক্ষেত্রে আমরা একবারে সব ডাটা আনি না। আমরা Pagination Parameters ব্যবহার করি:

- _page=1&_limit=10: মানে ১ নম্বর পেজের প্রথম ১০টি ডাটা দিন।
- পরবর্তী রিকোয়েস্টে _page=2&_limit=10 পাঠানো হয়।

**Merging:** নতুন ডাটা পাওয়ার পর আমরা আগের ডাটার সাথে তা যোগ করি: [...oldItems, ...newItems]। এখানে Set-based Filtering করতে হয় যাতে ডুপ্লিকেট কি (Key) এরর না আসে।

**৩. পারফরম্যান্স চ্যালেঞ্জ (Performance Challenges)**
*** ক. ডোম সাইজ (DOM Size)***
- আপনি যদি ১০,০০০ আইটেম লোড করেন, ব্রাউজারের DOM অনেক ভারী হয়ে যাবে এবং স্ক্রল করার সময় সাইট কাঁপতে (Stutter) শুরু করবে।

    - সমাধান: Windowing বা Virtualization। এটি কেবল সেই আইটেমগুলোই DOM-এ রাখে যা ইউজার স্ক্রিনে দেখছে। বাকিগুলো সরিয়ে ফেলে।

***খ. রিকোয়েস্ট থ্রটলিং (Request Throttling)***
ইউজার যদি খুব দ্রুত স্ক্রল করে, তবে একসাথে অনেকগুলো API কল চলে যেতে পারে। এটি আটকাতে আমরা একটি loading স্টেট ব্যবহার করি। যতক্ষণ একটি রিকোয়েস্ট শেষ না হয়, পরবর্তী রিকোয়েস্ট পাঠানো হয় না।

***৪. ইউজার এক্সপেরিয়েন্স (User Experience - UX)***
Skeleton Screens: ডাটা লোড হওয়ার সময় ফাঁকা জায়গা না রেখে একটি ঝাপসা (Blurred) প্রিভিউ দেখানো হয় যা ইউজারকে মনে করায় অ্যাপটি খুব দ্রুত কাজ করছে।

The Bottom-less Pit: ফুটার বা কন্টাক্ট ইনফরমেশন যদি ফিডের নিচে থাকে, তবে ইউজার সেখানে কখনোই পৌঁছাতে পারবে না। তাই ইনফিনিট স্ক্রল ফিডে ফুটার রাখা উচিত নয়।

**৫. সম্পূর্ণ প্রসেস ফ্লো (Step-by-Step Flow)**
- ১. Page 1 লোড: অ্যাপ চালু হলে প্রথম ১০টি পোস্ট দেখায়।
- ২. অবজারভার সেটআপ: লিস্টের একদম শেষ আইটেমটিকে "Target" হিসেবে মার্ক করা হয়।
- ৩. স্ক্রলিং: ইউজার স্ক্রল করে নিচে নামে।
- ৪. ইন্টারসেকশন: শেষ আইটেমটি যখন স্ক্রিনে দেখা যায়, Intersection Observer সেটি ডিটেক্ট করে।
- ৫. পরবর্তী পেজ রিকোয়েস্ট: page নম্বর বাড়িয়ে সার্ভারে নতুন রিকোয়েস্ট পাঠানো হয়।
- ৬. ক্লিন আপ: নতুন ডাটা আসার পর পুরনো অবজার্ভারটি সরিয়ে আবার নতুন লিস্টের শেষ আইটেমে অবজার্ভার লাগানো হয়।

### ইনফিনিট স্ক্রল: মেমরিতে ডাটা জমা হওয়ার ধাপসমূহ
ইনফিনিট স্ক্রল আসলে একটি "Accumulation" বা জমানোর প্রক্রিয়া। নিচে দেখুন ধাপে ধাপে কী ঘটে:

**ধাপ ১: ইনিশিয়াল স্টেট (Initial State)**
 - যখন পেজটি প্রথম লোড হয়, তখন আপনার React এর items স্টেটটি খালি থাকে [] এবং পেজ নম্বর থাকে 1।
    - Memory Status: RAM একদম ক্লিন।

**ধাপ ২: প্রথম ডাটা লোড (First Fetch)**
API থেকে প্রথম ১০টি ডাটা আসলো। আমরা setItems(data) করে সেই ১০টি ডাটা স্টেটে রাখলাম।

- Browser View: ইউজার স্ক্রিনে ১ থেকে ১০ নম্বর পোস্ট দেখছে।
- Memory Status: ১০টি অবজেক্ট ব্রাউজারের মেমরিতে (State) জমা হলো।

**ধাপ ৩: স্ক্রলিং এবং সেন্টিনেল ট্রিগার (Scrolling & Sentinel)**
ইউজার যখন স্ক্রল করে ১০ নম্বর পোস্টের কাছে পৌঁছায়, তখন Intersection Observer সিগন্যাল দেয়। আপনার কোড তখন পেজ নম্বর বাড়িয়ে 2 করে এবং নতুন API কল পাঠায়।

**ধাপ ৪: ডাটা মার্জিং (The Merging Step - CRITICAL)**
এটিই আসল জায়গা যেখানে পুরনো ডাটা মেমরিতে থেকে যায়। আমরা সাধারণত কোডটি এভাবে লিখি:
setItems(prev => [...prev, ...newData])

- কী ঘটছে? এখানে ...prev মানে হলো আগে যে ১০টি পোস্ট মেমরিতে ছিল, সেগুলোকে আমরা রেখে দিচ্ছি এবং তার পেছনে নতুন আসা ১০টি পোস্ট যোগ করছি।

- Memory Status: এখন মেমরিতে মোট ২০টি অবজেক্ট। ব্রাউজারকে এখন এই ২০টি আইটেম রেন্ডার করতে হচ্ছে।

**ধাপ ৫: চক্রবৃদ্ধি হারে মেমরি বৃদ্ধি (Memory Growth)**
ইউজার যত বেশি নিচে নামবে (Page 3, 4, 5...), আপনার items অ্যারে তত বড় হতে থাকবে।

- ১০০ বার স্ক্রল করলে মেমরিতে ১,০০০টি পোস্ট জমা হবে।

- ব্রাউজার এই ১,০০০টি পোস্টেরই DOM এলিমেন্ট (HTML) মেমরিতে ধরে রাখবে।
---

**সমস্যা: "The Memory Leak" বা স্লো হয়ে যাওয়া**
ইউজার যখন ১,০০০ বা ৫,০০০ পোস্ট পর্যন্ত নিচে নামবে, তখন দুটি বড় সমস্যা দেখা দেয়:

- RAM Consumption: ব্রাউজার অনেক বেশি মেমরি ব্যবহার করতে শুরু করবে।

- DOM Heavy: ব্রাউজারকে ১,০০০টি পোস্টের জন্য ১,০০০ সেট HTML এলিমেন্ট ম্যানেজ করতে হবে। ফলে স্ক্রল করার সময় সাইট কাঁপবে বা ল্যাগ করবে।

**সলিউশন: মেমরি কীভাবে ক্লিন রাখা যায়? (Senior Approach)**
প্রফেশনাল লেভেলে এই সমস্যা সমাধানের জন্য আমরা "Virtualization" (উইন্ডোয়িং) ব্যবহার করি।

থিওরি: মেমরিতে ডাটা সব থাকবে (অ্যারে হিসেবে), কিন্তু ব্রাউজারের DOM-এ শুধুমাত্র সেই ৫-১০টি পোস্ট থাকবে যা ইউজার বর্তমানে স্ক্রিনে দেখছে। বাকিগুলো DOM থেকে সরিয়ে ফেলা হবে কিন্তু ডাটা হিসেবে মেমরিতে থাকবে। এতে ব্রাউজার অনেক ফাস্ট কাজ করে।
---

### What is Virtualization? 
আমরা যে পদ্ধতিটি ব্যবহার করেছি তাকে বলা হয় "Standard Infinite Scroll"। এটি ১০-২০টি পেজ বা ২০০-৩০০ আইটেম পর্যন্ত খুব ভালো কাজ করবে, কিন্তু যখনই ডাটা আরও বাড়বে (যেমন ১০০০+ আইটেম), তখনই ব্রাউজার স্লো হতে শুরু করবে।

**১. আমাদের বর্তমান কোডে কী ঘটছে? (The "No Virtualization" Reality)**
আমরা নতুন ডাটা পাওয়ার পর setItems([...prev, ...newData]) করছি। এর মানে হলো:

- আপনি যদি ১০০ বার স্ক্রল করেন, ব্রাউজারের DOM-এ এখন ১০০০০টি পোস্টের HTML এলিমেন্ট আছে।
- ইউজার যখন নিচে থাকে, তখন উপরের ১ নম্বর পোস্টটি স্ক্রিনে না থাকলেও ব্রাউজারের মেমরিতে (DOM Tree) সেটি রয়ে গেছে। ব্রাউজারকে ওই অদৃশ্য ১০০০টি পোস্টের স্টাইল, লেআউট এবং পজিশন ক্যালকুলেট করতে হচ্ছে।

**২. ভার্চুয়ালিজেশন থাকলে কী হতো? (The "Virtualization" Approach)**
ভার্চুয়ালিজেশন বা উইন্ডোয়িং (Windowing) কনসেপ্টটি হলো একটি "স্লাইডিং উইন্ডো" এর মতো।

- মেমরি: আপনার জাভাস্ক্রিপ্ট ভেরিয়েবলে (Array) ১০০০টি ডাটা থাকবে।
- DOM: কিন্তু ব্রাউজারের স্ক্রিনে (HTML-এ) শুধুমাত্র ৫-১০টি পোস্ট থাকবে।
- কাজ করার পদ্ধতি: ইউজার যখন নিচে নামবে, তখন উপরের যে পোস্টগুলো স্ক্রিন থেকে হারিয়ে যাচ্ছে, ভার্চুয়ালিজেশন সেগুলোকে DOM থেকে ডিলিট করে দিবে এবং নিচের নতুন পোস্টগুলো অ্যাড করবে।

**৩. ভার্চুয়ালিজেশন কেন আমরা শুরুতে ব্যবহার করিনি?**
একজন Senior Frontend Engineer হিসেবে আপনাকে জানতে হবে কখন কোন অস্ত্র ব্যবহার করতে হয়:

- Standard Infinite Scroll: যখন ডাটা লিমিটেড এবং প্রতিটি পোস্টের হাইট (Height) ফিক্সড নয় (যেমন ফেসবুক বা টুইটার ফিড), তখন এটি সহজ এবং কার্যকর।

- Virtualization: যখন ডাটা অনেক বড় এবং পারফরম্যান্স সবথেকে বেশি জরুরি (যেমন কন্টাক্ট লিস্ট বা বিশাল ডাটা টেবিল), তখন এটি বাধ্যতামূলক।

**৪. ভার্চুয়ালিজেশন ব্যবহারের চ্যালেঞ্জ**
ভার্চুয়ালিজেশন ইমপ্লিমেন্ট করা বেশ জটিল, কারণ:

- প্রতিটি পোস্টের হাইট (Height) জানতে হয়। পোস্টের হাইট যদি আলাদা আলাদা হয় (Dynamic Height), তবে ক্যালকুলেশন অনেক কঠিন হয়ে যায়।

- স্ক্রল করার সময় কন্টেন্ট "ঝিকিমিকি" (Flickering) করতে পারে যদি পজিশনিং ঠিক না হয়।
